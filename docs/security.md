# Security notes

Postmote is an early implementation and has not received an independent security audit. It is not production ready. See `IMPLEMENTATION_STATUS.md` for missing release gates.

The HTTP service binds to loopback and checks Host and Origin. Owner sessions use an HttpOnly, SameSite=Strict cookie; owner passwords are scrypt-hashed. Agent tokens are random bearer credentials stored as hashes, and mailbox tools check explicit grants. A send request to an arbitrary recipient requires approval through an authenticated owner session. An agent assigned a dedicated inbox can send directly only to the owner-configured personal address; the direct-send tool accepts no recipient parameter. IMAP and SMTP require verified TLS or STARTTLS. Request bodies and credentials are not intended for logs.

Mailbox credentials and queued message bodies use AES-256-GCM. The master key defaults to a separate file in the same user data directory, protected by owner-only POSIX permissions where supported. `POSTMOTE_MASTER_KEY_FILE` can place it outside that directory. This protects against a database-only disclosure, but does not protect against another process running as the same user or theft of the whole data directory. Windows ACL enforcement and an OS keychain or passphrase unlock are not implemented.

Approval checks a hash of the reviewed stored payload. Send transitions are recorded without message bodies, and a configurable hourly submission limit applies. The workflow lacks complete auditing and integration tests for SMTP failures and crashes. Stdio opens the data store directly. Message contents are untrusted input and should never be treated as instructions. MIME parsing, attachment protections, background sync, and other planned operations remain incomplete. No claim is made that the current implementation satisfies the security or production acceptance criteria in the project plan.
