# Implementation status

The implementation is an early release and does not yet meet the production release gates in `POSTMOTE_IMPLEMENTATION_PLAN.md`. Do not describe it as production ready.

| Phase | Status | Evidence / remaining work |
|---|---|---|
| P0 Research and bootstrap | Partial | Bun/TypeScript, locked dependencies and basic reuse/security notes exist. A compiled Linux binary passes the sandbox mail integration; a full dependency and license audit remains. |
| P1 State, secrets and mail core | Partial | SQLite, a local key-file vault, account setup, connection checks, Thunderbird settings discovery, and bounded on-demand IMAP reads exist. Server-side search, folder listing, bounded plain-text MIME parsing and attachment chunks are available for messages up to 25 MiB, with a 10 MiB attachment limit. HTML output and streaming without buffering the full message remain. Mailbox settings can be updated or removed; changing IMAP identity clears the local index. The compiled Linux binary passes an authenticated implicit-TLS GreenMail test and refuses STARTTLS downgrade; real STARTTLS success and broader TLS scenarios remain untested. Saved password import uses Thunderbird’s NSS store and has been tested on Linux; macOS/Windows NSS loading still needs native verification. OAuth is unsupported. |
| P2 Approval system | Partial | An agent can queue plain-text mail for owner approval. Per the owner’s requested exception, a dedicated agent inbox can send directly to the configured personal address; other recipients still require approval. Approvals bind the reviewed stored payload with a hash. The send-request API accepts a client idempotency key. Editable plain-text drafts use revision checks and send requests snapshot their contents. An hourly submission limit and metadata-only send transition audit exist. A compiled-daemon integration test kills the process during SMTP DATA and verifies recovery to unknown without replay. Attachment forwarding and a broader audit trail remain. |
| P3 MCP API | Partial | Scoped HTTP and stdio transports provide account listing, status, folder discovery, message listing/source retrieval, paged search, parsed text and attachment chunks, draft/reply/forward preparation, flag/move/Trash operations, polling, send requests and send status. Scoped account, status and message resources and the three basic prompts are exposed. Portions of their planned argument contracts and several tool contract features remain incomplete. Stdio accesses SQLite directly rather than forwarding to the daemon. |
| P4 UI and operations | Partial | Owner setup/login, mailbox creation, agent creation/grants and approval queue exist. INBOX polling indexes bounded batches with UIDVALIDITY reset and deletion/flag reconciliation, retry backoff, jitter and cross-process leases. Existing agent grants, dedicated inbox assignments, mailbox settings and the personal email address can be edited in the dashboard. Send activity and a backup command are available; an inbox UI remains. |
| P5 QA and release | Incomplete | Local unit, HTTP, stdio and installer tests exist. CI exercises the compiled binary with an isolated local IMAP/SMTP server. A local browser check covered setup, profile discovery, permissions and approval review. The owner confirmed receipt of one live message sent through the selected Thunderbird SMTP account. Cross-platform protocol, broader browser/security, performance and full crash-recovery acceptance gates remain incomplete. No current release should be labeled production-ready. |

The secret key defaults to an owner-readable file alongside the database; `POSTMOTE_MASTER_KEY_FILE` can place it elsewhere. File permissions provide local-user separation, but this is not an OS keychain or a user-unlocked vault. Production use requires a stronger unlock model and independent security review.
